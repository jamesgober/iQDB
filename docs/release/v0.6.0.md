# iqdb v0.6.0 — Async Surface

**Drive iQDB from Tokio without blocking the executor.** v0.6.0 adds an opt-in `async` feature and `AsyncIqdb` — a Tokio adapter over the synchronous `Iqdb` handle. It is purely additive: the default build, the dependency set, and the entire synchronous API are unchanged, and no Tokio is pulled unless the `async` feature is enabled.

## What is iqdb?

An embedded vector database for Rust — a single-process, in-application similarity-search engine for high-dimensional workloads. As of v0.5.0 it is the integration layer over the iqdb crate family: exact and approximate search, declarative filters, durable storage, and an optional result cache, all behind one small handle.

## What's new in 0.6.0

### `AsyncIqdb` — a thin Tokio adapter

The family is synchronous by design. A nearest-neighbour search is a CPU-bound scan or graph walk; a durable write is a blocking `fsync`. Neither is async I/O, so wrapping the work in a future buys nothing — and blocking it on the executor thread would stall every other task on the runtime. The right place for async is the engine boundary, offloading the blocking call onto a dedicated pool.

`AsyncIqdb` does exactly that. It holds an `Arc<Iqdb>` and runs each operation through `tokio::task::spawn_blocking`:

```rust,ignore
use iqdb::{AsyncIqdb, DistanceMetric, Result, Vector, VectorId};

#[tokio::main]
async fn main() -> Result<()> {
    let db = AsyncIqdb::open_in_memory(3, DistanceMetric::Cosine).await?;
    db.upsert(VectorId::from(1u64), Vector::new(vec![1.0, 0.0, 0.0])?, None).await?;

    let hits = db.search(Vector::new(vec![1.0, 0.0, 0.0])?, 1).await?;
    assert_eq!(hits[0].id, VectorId::from(1u64));
    db.close().await
}
```

The async surface mirrors the sync one: `open_in_memory` / `open_in_memory_with` / `open` / `open_with`, `upsert`, `get`, `delete`, `search`, `search_with`, `search_batch`, `search_batch_with`, `optimize`, `flush`, `close`. Search and batch methods take their query **by value**, since the work runs on another thread. Cheap, non-blocking accessors (`len`, `is_empty`, `dim`, `metric`, `cache_stats`) stay synchronous — there is nothing to offload.

### Concurrency

`AsyncIqdb` is `Clone` (it shares the underlying handle through the `Arc`), `Send`, and `Sync`, so it fans out naturally across tasks:

```rust,ignore
let db = std::sync::Arc::new(AsyncIqdb::open_in_memory(2, metric).await?);
let mut tasks = Vec::new();
for q in queries {
    let db = std::sync::Arc::clone(&db);
    tasks.push(tokio::spawn(async move { db.search(q, 10).await }));
}
```

A panic inside a blocking closure (a bug, since library code does not panic on valid input) is re-raised on the awaiting task rather than swallowed; `spawn_blocking` tasks are not cancellable, so that is the only failure a join can carry.

### Bring your own runtime

The `async` feature pulls only `tokio` with its `rt` feature — `spawn_blocking` is all that is needed. The caller supplies the runtime. The default build remains Tokio-free.

## Breaking changes

**None.** The synchronous `Iqdb` surface is unchanged. `AsyncIqdb` and the `tokio` dependency only exist when the `async` feature is enabled.

## Verification

Run on Windows x86_64 and on WSL2 Ubuntu (Rust stable); the same commands run in the configured CI matrix on Linux, macOS, and Windows:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --features async -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo test
cargo test --features async
cargo test --all-features
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo +1.87 build
cargo run --example async_search --features async
```

All green. Test counts with `--features async`: 37 unit (incl. 3 async) + 3 async integration + 10 persistence + 2 property + 3 recall + 19 doctests. The default build (async off) is byte-for-byte the v0.5.0 surface — 34 unit + 32 integration + 17 doctests, no Tokio linked.
